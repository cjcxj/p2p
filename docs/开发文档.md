## 1. 项目概述

### 1.1 定位

**跨平台、SDK-first、轻量级的 P2P 虚拟网络与实时连接基础设施**（定位取自 `docs/design/文档1.md`）。

具体形态：任意 NAT 环境下的多个节点组成一个带**虚拟 IP 子网**的私有网络，支持**多跳网状路由**、**广播/组播仿真**，并可在 Windows / Linux 创建 **TUN 虚拟网卡**、在 Android 通过 **VpnService** 接入，让操作系统流量直接走组网。纯 Go 实现，同一核心同时产出：

| 产物 | 形态 |
|---|---|
| Windows / Linux | CLI 客户端（`p2p-client`）+ 三合一服务器（`p2p-server`） |
| Android | `p2p.aar`（gomobile 绑定，Java/Kotlin 直接调用） |
| 任意 Go 应用 | `p2p/sdk` 包 |

### 1.2 核心能力

| 能力 | 实现位置 |
|---|---|
| 虚拟 IP + 子网 | 服务器按房间从 `--network` 分配（默认 10.9.0.0/24），节点按 IP 寻址 |
| 多跳网状路由 | 泛洪 + TTL + 包去重，任意拓扑可达 |
| 广播 / 组播仿真 | 子网广播地址与组播范围在虚拟网络内泛洪 |
| NAT 检测 | RFC 3489 行为探测 + 对称端口增量测量 |
| UDP 打洞 | 4 类 NAT 任意组合的策略矩阵 + 对称端口预测 |
| 中继回退 | 类 TURN 房间级中继（房间 token 鉴权），可关闭 |
| 双向鉴权 | HMAC-SHA256 挑战-应答，双向验证，防伪服务器/未授权客户端 |
| TUN 虚拟网卡 | Windows（wintun）/ Linux（/dev/net/tun）；Windows 自动加防火墙放行规则 |
| 用户态 IP 栈 | gVisor netstack：Android 上进程内应答 ICMP / 转发 TCP |

### 1.3 平台支持矩阵

| 平台 | 接入方式 | 虚拟网卡 | 用户态应答 | 限制 |
|---|---|---|---|---|
| Windows | CLI（`p2p-client`） | TUN（wintun，自动加防火墙放行规则） | — | TUN 需管理员；wintun.dll 随 exe 同目录分发 |
| Linux | CLI（`p2p-client`） | TUN（/dev/net/tun） | — | 需 root |
| Android | `p2p.aar`（gomobile） | VpnService（`android-demo` 内置 `MeshVpnService`） | gVisor：进程内 ICMP 应答 + TCP 转发 | 需 INTERNET 权限与 VPN 授权弹窗 |
| Go 应用 | `p2p/sdk` 包 | 可选（`core/tundev`） | `EnableLocalStack()` / `ExposeTCP()` | 应用数据为事件式；L7 stream 待路线图 P3 |

## 2. 技术选型与决策记录

项目起源于两份设计讨论（`docs/design/文档1.md`、`docs/design/文档2.md`）。本节记录**设计建议 → 最终落地**的决策过程，作为后续架构讨论的基线。

| 关注点 | 文档1 建议 | 文档2 建议 | 实际落地 | 说明 |
|---|---|---|---|---|
| 核心语言 | Rust（native 库 + 多平台 FFI） | **纯 Go** | **纯 Go** | 采用文档2 决策：Go 单 socket + goroutine 并发模型足够，gomobile 直出 AAR，避免 FFI 成本 |
| 信令 | Controller | WebSocket | **JSON-over-TCP**（长度前缀帧） | 无浏览器端需求，TCP 更简单；格式见 §6.1 |
| 加密 | WireGuard/Noise | Noise XK（X25519+ChaCha20-Poly1305） | **信令层 HMAC-SHA256 双向鉴权；数据面 X25519 + HKDF + ChaCha20-Poly1305（候选交换自动协商）** | 采用 §11.4 方案 B；旧版互操作自动回退明文 |
| 数据面 | Encrypted UDP | UDP 数据报（单 socket） | **UDP 单 socket**（与 STUN 检测共用） | 已落地 |
| 打洞 | STUN + Hole Punch | STUN + 并发打洞 + TURN 兜底 | **STUN + 双向同时探测 + 端口预测 + 中继兜底** | 另加「对称↔对称直接走中继/多跳」的经验规则 |
| L3 网卡 | 各平台 TUN | water / gVisor netstack | **wireguard/tun**（Win/Linux）+ **gVisor netstack**（Android 应答） | 与文档2 思路一致，选型不同 |
| 中继 | Relay（独立服务） | TURN 中继 | **房间级 UDP 中继，与 STUN 复用同一端口** | 单端口部署简化运维 |
| 虚拟网 | 10.66.0.2 等 | 10.99.0.0/16 | **10.9.0.0/24**（可配置），服务器按房间分配 | 分配算法见 §5.4 |
| 多跳路由 | 未提及 | 未提及 | **泛洪多跳 mesh 路由**（本项目原创点） | 无法直连的节点经中间节点可达 |
| SDK 分层 | High / Network / Low 三层 | L3 + L7 两层 | **单层 Session API**（L3 数据报语义） | 三层拆分与 L7 stream/datagram 在路线图 P3（§13） |

**未采纳/待办清单**（设计文档提出、当前未实现）：

- 文档1：iOS/macOS 平台、三层 SDK 拆分、`onPathChanged` / `onNetworkChanged` / 网络切换自动重打洞、连接统计（rtt/packetLoss/bytes）、CLI `p2p up/down/status` 形态、systemd/Docker 打包
- 文档2：L7 stream/datagram/pub-sub、保活包（`DgramKeepAlive`）、双路径择优切换、批量 IO / sync.Pool 低延迟优化
- 文档2 原案的 Noise XK 数据面加密未照搬，已用更轻量的方案 B（候选携带 X25519 公钥 + HKDF + AEAD）实现，见 §11.4

> 已归档：`文档1.md`、`文档2.md` 已移入 `docs/design/`，本文档作为唯一事实来源（source of truth）。

## 3. 总体架构

### 3.1 分层图（现状）

```text
┌────────────────────────────────────────────────────────┐
│  应用层                                                   │
│  Go: sdk.Session + Listener     Android: p2p.aar         │
│  CLI: cmd/client                Android demo (VpnService)│
├────────────────────────────────────────────────────────┤
│  sdk/           连接流水线编排、成员管理、事件分发          │
├────────────────────────────────────────────────────────┤
│  core/mesh      虚拟 IP 寻址、泛洪多跳路由、广播、去重      │
│  core/punch     UDP 打洞引擎、策略矩阵、中继客户端          │
│  core/stun      STUN 编解码/服务器、NAT 分类               │
│  core/signaling JSON-over-TCP 信令（客户端+服务器+房间）    │
│  core/relay     类 TURN UDP 中继（共享 socket）            │
│  core/auth      HMAC-SHA256 双向挑战-应答                 │
│  core/netstack  gVisor 用户态 IP 栈（Android）            │
│  core/tundev    TUN 网卡（Windows wintun / Linux）        │
│  core/protocol  共享 wire 类型（PeerID/消息/候选）          │
├────────────────────────────────────────────────────────┤
│  传输层        UDP（打洞+STUN+中继 共用）  TCP（信令）      │
└────────────────────────────────────────────────────────┘
```

### 3.2 服务器形态

`cmd/server` 是三合一服务器，**默认只占用一个端口**：

```text
:8080/TCP ── 信令（房间管理、虚拟 IP 分配、候选转发、鉴权）
:8080/UDP ── STUN 应答 ─┐
:8080/UDP ── 中继转发 ──┴─ 同一个 UDP socket，按 magic 解复用（见 §6.6）
可选 :8081/UDP ── STUN 副端口（--stun-secondary，change-port 测试用）
可选 <IP2>:8080/UDP ── STUN 第二 IP（--stun-ip2，change-IP 测试用）
```

### 3.3 客户端连接流水线

`Session.Connect` 异步执行 7 步（`sdk/session.go:327` 的 `run`）：

```text
1. NAT 检测        STUN over 共享 UDP socket（RFC 3489 测试序列，§5.3）
2. 信令握手        TCP：hello → (challenge → auth → auth_ok) → welcome
                  → relay_grant? → members（获得 PeerID + 虚拟 IP + 子网）
3. 创建 mesh 节点  注册 OnData 回调（→ EventData 或 localStack）
4. 启动打洞引擎    同一 UDP socket 上的 Punch（读循环）
5. 运行信令读循环   候选交换 / 成员同步 / 中继授权
6. 候选交换        对每个新成员互发 Candidate（NAT 类型/公网/私网/增量/中继/X25519 公钥）
7. 看门狗          TimeoutSec+5s 后若无可达节点报 EventError
```

### 3.4 端到端时序（两节点打洞直连）

```text
Node A                 Server                  Node B
  │ hello ──────────────▶│◀────────────── hello  │
  │ ◀───────── welcome   │   welcome ──────────▶ │
  │ ◀───────── members   │   members ──────────▶ │
  │ candidate(B) ────────▶│──────── candidate(A)▶ │
  │                      │                       │
  │════ UDP 双向同时探测（LAN→公网→预测端口）═════│
  │ ◀────────────────────│─────────────────────▶ │
  │        probe/ack 到达即 established          │
  │═════════════════ 直连（punched）═════════════│
  │                      │                       │
  │ （超时 4s 仍未通）    │                       │
  │ reg("room\0token") ─▶│◀───────────────────── │
  │ ◀── reg_ack（中继已登记）                     │
  │══════════ 经中继互通（relay）═════════════════│
```

## 5. 核心模块设计

### 5.1 `core/protocol` — 共享 wire 类型

- `PeerID`：16 字节随机标识，服务器分配，32 位小写 hex 字符串表示（`crypto/rand`）。
- `Message`：信令 JSON 帧结构（字段见 §6.1.3）。`omitempty` 字段必须保留——线上新旧版本兼容依赖它。
- `Candidate`：打洞候选（peer_id / virtual_ip / nat_type / public_addr / private_addr / relay_addr / port_delta / x25519_pub）。`x25519_pub` 为 v0.4 新增，用于数据面 AEAD 协商。

### 5.2 `core/auth` — 双向鉴权

```
credKey     = HMAC-SHA256(secret, "p2p-auth-v1"[:user])
clientProof = HMAC-SHA256(credKey, "client:<clientNonce>:<serverNonce>")
serverProof = HMAC-SHA256(credKey, "server:<serverNonce>:<clientNonce>")
```

- 服务器侧 `authenticate`（`signaling/server.go:276`）在 hello 之后、房间加入之前执行，失败即断连。
- 客户端侧防降级：配置了凭证但服务器不发起挑战 → 客户端主动拒绝（`signaling/client.go:99`）。
- `auth.Equal` 用 `hmac.Equal` 常数时间比较；nonce 为 16 字节随机 hex。
- 服务器支持两种模式：`--secret` 共享 PSK；`--users user:pass,...` 按用户派生不同密钥（`authConfig.keyFor`）。

### 5.3 `core/stun` — NAT 检测与 STUN 服务器

**客户端分类决策树**（`stun/nat.go:62`）：

```text
Test I  绑定主服务器: mapped == 本地 socket 地址 → open
Test III 带 change-port 请求（由服务器 port+1 应答）:
   有应答 → Test II 带 change-IP 请求（由服务器第二 IP 应答）:
       有应答 → full_cone
       无应答 → restricted_cone
   无应答 → 向第二目的地(port+1)再绑定:
       映射端口不同 → symmetric（PortDelta = p2 - p1）
       映射端口相同 → port_restricted_cone
```

退化行为（重要）：单 IP 单端口服务器**故意静默**不答 change 请求，客户端保守分类——full-cone 会被判成 restricted-cone（对打洞等价）；测不出 delta 的对称 NAT 判为 port_restricted_cone。

**服务器应答**（`stun/server.go:114` `AnswerBinding`）：按 CHANGE-REQUEST 从主 socket / 副端口 socket / 第二 IP socket 择一应答；无法满足 change 请求时**保持静默**而非拒绝。

### 5.4 `core/signaling` — 信令服务器与房间管理

- 帧编解码：4 字节大端长度前缀 + JSON，单帧上限 1 MiB（`frame.go`）。
- `Hub` 管理房间：房间由**首个加入者**创建（其 token 成为房间密钥，后续必须一致）；无 token 房间不设防。
- 虚拟 IP 分配（`hub.go:80` `assignIP`）：从 host 位 1 开始按序分配，**最多 254 个主机地址**（`i=1..254`，与子网大小无关，/16 也只用到低 8 位）；成员离开时释放（`freeOnLeave`）。
- 成员同步：全量列表广播（join 时发给所有人 + leave 时重发），客户端做差集做 join/leave 判定。
- 连接回收：`reapLoop` 每 15s 检查，75s 静默即关连接释放虚拟 IP；客户端每 25s 发 `ping` 心跳。
- 服务器并发模型：每连接一 goroutine；成员写连接走 `member.mu` 串行化，避免广播/转发帧交错。
- 限流：`--max-conns-per-ip` 限制每源 IP 并发信令连接数；`--max-room-members` 限制每房间成员数（`Hub.SetMaxMembers`）。
- 候选转发：按 `msg.Candidate.PeerID` 路由到同房间成员（跨房间不可达）。

### 5.5 `core/punch` — 打洞引擎

**策略矩阵**（`strategy.go:48` `planTargets`，双方同时应用）：

```text
1. lan        双方私网地址同 /24 前三字节（EnableLAN）→ 私网直连
2. public     始终探测（所有 cone 组合、部分对称都靠它）
3. predicted  symmetric 端口窗口：base + k*delta, k∈[-4, +8]
              （delta 未知时退化为 base+1..base+4）
4. relay      双路径：与直连目标并行探测（v0.19），先通先用，后续直连打通自动切换
```

- **对称↔对称特例**（`punch.go:199`）：预测链路会立即失效，若中继可用直接 relay-only；中继关闭时放弃直连，交给 mesh 多跳。
- 连通判定：收到**已知 peer** 的 probe/ack 即 established（探测包 dst 为空，靠 src 识别对端）；`classifyTransport` 比较来源地址与中继地址得到 `punched`/`relay`。
- 探测循环：`probeLoop` 每 200ms 对全部目标发一轮，直到 connected / 引擎停止；每个 peer 有独立 `stop` 通道，`AddPeer` 刷新候选会先停旧循环再启新循环，`RemovePeer` 也会终止对应循环（K2 已修复）。
- 中继注册：`RegisterRelay` 每 200ms 重发 `room\0token` 注册包直到停止（无状态中继靠重发保活）。
- 双路径：中继与直连同时探测；若中继先通则先用 relay，后续 punched 打通时通过 `EventPathChanged` 自动切换（v0.19）。
- 保活：连接建立后 `probeLoop` 转入 `keepaliveLoop`，每 15s 向已确认 endpoint 发一次目标限定的 ack，维持 NAT 映射（K3 已修复）。
- 链路自愈：若已连接 peer 超过 45s 未收到任何包，引擎将该 peer 标记为未连接并自动重新执行打洞（`restartPeer`）。

### 5.6 `core/relay` — 类 TURN 中继

- 单 UDP socket 服务所有房间（`UseConn` 模式与服务器主 socket 复用，也可 `Bind` 独立监听）。
- 状态：`rooms[roomID] → {token, members[peerID] → UDPAddr}`。
- 注册包 `room\0token`：token 匹配才登记并回 `reg_ack`；**每收到该成员任何包都刷新其映射地址**（适配对称 NAT）。
- 注册加固：v0.9 起信令为每个成员签发独立 relay token（`relay_grant.relay_token`），中继按 `peerID → token` 校验；其他成员无法用自己 token 冒充他人。旧客户端仍可用房间 token 注册（兼容回退）。
- 限流：`MaxRoomMembers` 与信令侧保持一致，超过上限的新 UDP 成员注册会被拒绝（已注册成员不受影响）。
- 转发：将成员包广播给同房间**其他所有**成员（不回环给发送者）。
- `Allocate(room, token, publicHost)` 按房间惰性创建，返回 `publicHost:port` 由信令下发给客户端（`RelayAlloc` 回调）。
- 局限：只验 token 不验身份（punch 帧 src 可伪造），见 §12 S2。

### 5.7 `core/mesh` — 虚拟网络层

- 帧格式与路由算法见 §6.3。
- `Node.SendTo(dst, payload)`：有直达链路（`byIP` 索引）走直连，否则优先走**已学习路由**，最后才泛洪。
- `Handle(from, frame)`：去重 → 学习 `src → from` 反向路由 → 目的地是本机则投递（`OnData`）→ 广播帧本地投递 → TTL 递减转发（不回发来源链路）。
- 广播目标判定：组播地址或子网广播地址（`n.Net` 计算）。
- 已知成员表：`AddKnownIP`/`RemoveKnownIP` 由 SDK 在成员同步时维护；未知单播目标直接丢弃，不再退化为全网泛洪（K7 已修复）。
- 去重表：`(srcIP, pktID)` 键，超过 8192 条按 FIFO 淘汰最旧条目，不再整体清空（K8 已修复）。

### 5.8 `core/netstack` — 用户态 IP 栈（gVisor）

- 场景：Android 内核不会替 VpnService tun 回包，故本机虚拟 IP 的入站包在进程内处理。
- `Wants(pkt)` 判定：目的 = 本机虚拟 IP 且（ICMP echo request 或任意 TCP）。
- ICMP echo：栈内直接应答；TCP：`gonet` 监听虚拟 IP，转发到本机 `127.0.0.1:port`（`ExposeTCP`，demo 用 7000 回显验证）。
- 出站回包经 `send` 回调回到 mesh（`SendToIP`）；入站包通过 `AddStaticNeighbor` 绕开 ARP。

### 5.9 `core/tundev` — TUN 网卡

- `Create(ip, mask, mtu)`：`wireguard/tun` 创建 `p2p%d`；Windows 要求 wintun.dll 与管理员权限；Linux 要求 root 与 /dev/net/tun。
- Windows 配置：`netsh interface ipv4 set address`（`windows.go`）。
- Linux 配置：`ip link set dev up` + `ip addr add`（`linux.go`）。
- Windows 防火墙：入站默认策略会丢 ICMP，`AddInterfaceFirewallRules` 加 ICMPv4/TCP/UDP/ANY × 入/出 共 8 条规则，按虚拟子网限定 `remoteip`（`firewall_windows.go`）；非 Windows 平台为 no-op。
- 辅助函数：`IPv4Destination`（从 IP 包取目的地址）、`IsBroadcastOrMulticast`（决定 mesh 广播或单播）。

## 6. 协议规范

> 改任何 wire 格式前必须先读本节，并更新本表与版本号。所有整数均为大端。

### 6.1 信令协议（JSON-over-TCP）

**帧格式**：`[4B BE 长度][JSON 载荷]`，长度 ≤ 1 MiB。

**消息类型**（`core/protocol/protocol.go:40`）：

| type | 方向 | 含义 |
|---|---|---|
| `hello` | C→S | 首个帧：room、token、（鉴权时）user、nonce |
| `challenge` | S→C | 服务器 nonce（要求客户端证明） |
| `auth` | C→S | 客户端 proof |
| `auth_ok` | S→C | 服务器 proof（客户端验真） |
| `welcome` | S→C | peer_id、virtual_ip、network |
| `relay_grant` | S→C | 中继地址 + 本成员专属 relay token（房间启用中继时） |
| `members` | S→C | 全量成员列表（peer_id + virtual_ip） |
| `candidate` | C→S→C | 打洞候选，按 candidate.peer_id 路由 |
| `ping` | C→S | 心跳（25s 间隔） |
| `leave` | C→S | 主动离开 |
| `error` | S→C | 错误（握手失败等） |

**Message JSON 字段**（Go struct 定义，tag 即 wire 名）：

```go
type Message struct {
    Type      string       `json:"type"`
    Room      string       `json:"room,omitempty"`
    Token     string       `json:"token,omitempty"`
    PeerID    string       `json:"peer_id,omitempty"`
    VirtualIP string       `json:"virtual_ip,omitempty"`
    Network   string       `json:"network,omitempty"`
    Members   []MemberInfo `json:"members,omitempty"`
    Candidate *Candidate   `json:"candidate,omitempty"`
    RelayAddr string       `json:"relay_addr,omitempty"`
    RelayToken string      `json:"relay_token,omitempty"`
    User      string       `json:"user,omitempty"`
    Nonce     string       `json:"nonce,omitempty"`
    Proof     string       `json:"proof,omitempty"`
    Error     string       `json:"error,omitempty"`
}
```

**握手时序**：

```text
无鉴权:  C→S hello ── S→C welcome + relay_grant? + members
有鉴权:  C→S hello(user, clientNonce)
         S→C challenge(serverNonce)
         C→S auth(proof=HMAC(key,"client",cNonce,sNonce))
         S→C auth_ok(proof=HMAC(key,"server",sNonce,cNonce))   ← 服务器验真后
         S→C welcome + relay_grant? + members
```

**时序约束**：服务器 75s 无活动回收连接；客户端 25s 心跳；候选由「新成员加入」与「收到对方候选」双向触发（每方对新成员主动发一次自己的候选）。

### 6.2 打洞帧（`PNCH`）

**帧布局**（`core/punch/packet.go`，头 41 字节）：

```text
0     4        5        7        23       39       41
┌───────┬───────┬────────┬────────┬────────┬────────┬──────────┐
│ magic │ type  │  seq   │  src   │  dst   │  len   │ payload  │
│ "PNCH"│  1B   │  2B    │  16B   │  16B   │  2B    │ ≤65535B  │
└───────┴───────┴────────┴────────┴────────┴────────┴──────────┘
```

| type | 值 | 说明 |
|---|---|---|
| probe | 1 | 探测包，dst 为零值（对端未定） |
| ack | 2 | 探测应答，dst = 对端 |
| data | 3 | 数据包，dst = 对端（payload 为 mesh 帧；双方协商加密后为 AEAD 密文，解密后才是 mesh 帧） |
| register | 4 | 中继注册（payload = `room\0token`），仅服务器消费 |
| reg_ack | 5 | 中继注册确认（src 为零值，dst = 客户端） |
| probe2 | 6 | 与 probe 等价的历史类型，收包侧同等处理 |

**接收过滤**：probe/probe2/ack/data 要求 `dst == 本机ID 或 零值`；reg_ack 要求 `dst == 本机ID`；register 客户端直接丢弃。

**连通状态机**：`probe/ack` 从已知 peer 到达即 `established`，随后 `OnState(punched|relay)` 上报、mesh 注册直连链路；此后 data 包按对端 ID 投递（IP 地址不可信，只用于 transport 归类）。

**数据面加密（v0.4）**：当双方候选都携带 `x25519_pub` 时，SDK 在发送 `PktData` 前把 mesh 帧封装为：

```text
payload = [12B 随机 nonce][ChaCha20-Poly1305 密文 + 16B tag]
```

密钥由 `HKDF-SHA256(X25519(私钥, 对端公钥), info="p2p-data-v1:<room>:<排序后的双方PeerID>")` 派生。加密在 SDK 的 `sendSecure` 完成，punch 帧头与 mesh 帧格式不变；对端无公钥时自动回退明文，保证与旧版互操作。probe/ack/register 等控制包不加密。链路加密是**逐跳**的：多跳转发时中间节点解密 mesh 帧后按目标转发，并用与下一跳的密钥重新加密。v0.22 起，**单播应用载荷还会在源节点用目的节点密钥做端到端加密（E2E）**，中间节点即使解开了逐跳链路加密也只能看到路由头，无法读取应用数据；广播仍为逐跳加密。

### 6.3 mesh 帧（`MSHM`）

**帧布局**（`core/mesh/mesh.go`，头 42 字节）：

```text
0     4      5     6       10       26       42
┌───────┬──────┬─────┬────────┬────────┬────────┬──────────┐
│ magic │flags │ TTL │ pktID  │  src   │  dst   │ payload  │
│ "MSHM"│  1B  │ 1B  │  4B    │  16B   │  16B   │          │
└───────┴──────┴─────┴────────┴────────┴────────┴──────────┘
```

- `flags`：`0x01` = broadcast（子网广播/组播仿真）。
- `TTL`：最大 16，每转发递减，≤1 不再转发。
- 去重键：`(srcIP, pktID)`，pktID 由发送方自增（回绕跳过 0）。
- 单播路由：优先直达链路；其次走已学习反向路由（v0.17）；无路由时泛洪（不发回来源链路，避免回声）。
- 广播：本地投递一次 + 转发所有其他链路。
- 目标 IP 不存在（不在已知成员表）的单播直接丢弃，不再退化为全网泛洪（K7 已修复）；已知成员但无直达链路时仍走泛洪多跳。

### 6.4 STUN（RFC 5389 最小实现）

- 标准 20B 头 + magic cookie `0x2112A442`；属性：MAPPED-ADDRESS / XOR-MAPPED-ADDRESS（优先）/ CHANGE-REQUEST / ERROR-CODE / SOFTWARE。
- 服务器只应答 BindingRequest，响应带 XOR-MAPPED-ADDRESS（`AnswerBinding`）。
- 客户端 `Detect()` 的测试序列与分类树见 §5.3；`PortDelta` 供对端预测窗口使用。

### 6.5 中继协议

- 注册：客户端周期性发 `register` 包，payload = `房间名 \0 token`。v0.9 起新客户端使用信令下发的**本成员专属 relay token**；旧客户端继续使用房间 token。
- 服务器：token 匹配（房间 token 或该 peer 的专属 token）→ 记录 `peerID → 源地址` → 回 `reg_ack`；此后该成员的任何包都**刷新地址**并广播给同房间其他成员。
- 客户端判定中继链路：punch 层按来源地址是否等于中继地址归类为 `relay`。

### 6.6 服务器 UDP 解复用

服务器主 UDP socket 读循环（`cmd/server/main.go:97`）按序判定：

```text
1. 前 4B == punch.Magic ("PNCH")  → 中继 Handle
2. offset4..8 == STUN cookie     → BindingRequest 则 AnswerBinding
3. 其他                          → 丢弃
```

### 7.2 Android（gomobile 绑定）

`android/p2p.aar` 由 `gomobile bind -target=android -androidapi 21 -o p2p.aar ./sdk` 生成，API 为 Go API 的 camelCase 映射：`Config()` / `Session(cfg, listener)` / `connect(room)` / `disconnect()` / `sendToIP(ip, data)` / `broadcast(data)` / `send(peerID, data)` / `localIP()` / `subnet()` / `natType()` / `members()` / `memberCount()` / `memberAt(i)` / `setSocketProtector(p)` / `enableLocalStack()` / `exposeTCP(port)`；常量在 `P2p` 类（`P2p.EventData`、`P2p.EventPathChanged` 等）。完整示例见 `android/example.kt` 与 `android-demo/`。

**集成步骤**：Import `.AAR` 模块 → `implementation project(':p2p')` → 声明 INTERNET 权限。回调来自 Go 线程，UI 需切主线程。

**VPN 接入要点**（`android-demo` 的 `MeshVpnService`）：
1. `setSocketProtector` **先于** VPN 建立（`protect(fd)` 防死循环）
2. `Builder`：只 `addRoute` 虚拟子网（手机正常上网不受影响）、MTU 1280、`setBlocking(true)`、Android 12+ `setUnderlyingNetworks`
3. `enableLocalStack` 让 ping/TCP 在进程内应答；ICMP 另有「内核优先 + 500ms 兜底 + 周期复探」三级策略
4. VPN 读循环按 `virtualNet/virtualPrefix` 丢弃非虚拟网段流量（二者在 `buildVpn` 中由 `s.subnet()` 解析赋值）

## 11. 质量属性：轻量化 / 高性能 / 低延迟 / 安全

本章按产品的四条硬性要求逐项评估现状、记录已落地的设计决策，并给出差距与设计提案。编号与 §12（问题清单）、§13（路线图）联动。

### 11.1 轻量化（Lightweight）

**现状证据**：

| 指标 | 数值 |
|---|---|
| 源码规模 | 45 个 Go 文件（含测试）、约 6953 行 |
| 二进制 | client 4.87–5.04 MB / server 2.84–2.99 MB（静态、`-trimpath -s -w`、CGO 关） |
| Android AAR | 16.43 MB（armeabi-v7a / arm64-v8a / x86 / x86_64 四 ABI） |
| 部署面 | 服务器单端口（TCP 信令 + UDP STUN/中继复用），防火墙只放行一个端口 |

**轻量的来源**：wire 协议全部手写大端编解码（无 protobuf/大框架）；单 UDP socket 复用全部 UDP 协议；平台差异用 build tags 隔离、公共逻辑零平台分支。

**新增代码的轻量原则**：
1. 不引入序列化/日志/配置框架，继续手写 wire 与 `flag`
2. 核心路径（`core/*`）禁止重依赖；gVisor 是当前最大的依赖，仅服务 Android 进程内应答——若 Android 侧确认可全走应用层 ICMP 兜底（demo 已具备该路径），可将 `netstack` 用 build tag 拆为可选，进一步缩小 AAR
3. 新平台接入（iOS/macOS）沿用「薄适配层 + 同一 core」模式，不 fork 核心

### 11.2 高性能（High Performance）

**已落地**：
- 单 UDP socket 全协议复用：STUN 检测、打洞探测、数据、中继全走一个 socket，syscall 与 socket 数量最小化
- 读循环 64 KB buffer 复用（`punch.go:292`），无逐包分配
- mesh 广播帧单次 `Encode`、多链路共享同一字节流（`mesh.go:230`）
- 每 peer 一条探测 goroutine + 一条共享读循环，无全局锁热区

**热点与优化提案**（对应文档2 低延迟清单）：

| # | 提案 | 位置 | 说明 |
|---|---|---|---|
| 1 | 批量收包 | `punch.readLoop` | 已实现（v0.20）：Linux 用 `ipv4.PacketConn.ReadBatch`，其他平台回退单包读取 |
| 2 | 缓冲池 | `punch` 热路径 | 已实现（v0.13）：`encodePooled` + `putEncode` 在 Send/probe/ack/register/keepalive 复用 `sync.Pool` 缓冲 |
| 3 | 注册退避 | `RegisterRelay` | 注册包固定 200 ms 重发，可指数退避 + 收到 reg_ack 后降频 |
| 4 | 微基准 | `core/punch`、`core/mesh` | 已建立 Encode/Decode benchmarks（v0.12）；mesh 转发与端到端 PPS 基线待补 |
| 5 | 路由收敛 | `core/mesh` | 已实现反向路由学习（v0.17）：收到帧即学习 `src → from`，单播优先走已学路由，泛洪降为兜底 |
| 6 | FEC | `core/fec` | 已实现 XOR 奇偶校验原语（v0.18）：一组等长包可恢复丢失的 1 个包 |

### 11.3 低延迟（Low Latency）

**已落地的延迟决策**：
- 数据面尽力而为 UDP 数据报：不重传、不排队，实时流量无队头阻塞（文档2 核心主张）
- 探测顺序：LAN → 公网 → 预测端口；中继自 v0.19 起并行探测，先通先用，直连打通后自动切换
- 对称↔对称跳过无望的预测探测，直接中继/多跳，不浪费往返
- 1 包即通：probe 或 ack 到达即 established，无多次握手
- 控制面开销极小：心跳 25 s、服务器回收 75 s

**延迟差距（待 P6 补齐）**：
- 已实现 15s keepalive、45s 静默超时检测与自动重打洞（P2 链路管理）
- RTT 探测已在 L7 提供（v0.16），FEC 原语已提供（v0.18），双路径并行探测已实现（v0.19）
- 已实现反向路由学习，泛洪仅作为未知路径兜底（v0.17）；进一步可做主动路由探测/度量
- TUN→mesh 单 goroutine 串行读（L3），高吞吐下排队延迟

### 11.4 安全（Security）

**威胁模型与现状对照**：

| 威胁 | 现状 | 差距 |
|---|---|---|
| 路径窃听（嗅探 UDP/TCP） | 数据面 X25519+ChaCha20-Poly1305 已防（S1 修复）；信令 TLS 已支持（v0.8） | — |
| 同房间恶意成员 | 数据面按 peer 对密钥加密，伪造 src 无法通过解密（S2 修复）；中继注册已按 per-peer token 加固（S3 部分修复） | 移除旧 room-token 回退（严格模式） |
| 伪服务器 | 客户端鉴权 + 防降级（✓ 已防） | 凭证暴力枚举无速率限制 |
| 伪客户端 | HMAC-SHA256 双向鉴权（✓ 已防） | 数据面与信令面凭证未联动 |
| 资源耗尽 | 已支持每 IP 连接数与每房间成员数上限（S4 部分修复） | 房间创建频率限制、中继注册加固 |

**已落地、值得保留的安全设计**：
- 双向挑战-应答（服务器验客户端 + 客户端验服务器）与防降级拒绝（`signaling/client.go:99`）
- 房间 token 门控信令与中继；per-user 密钥派生（用户间凭证隔离）
- 数据面 AEAD：X25519 临时密钥 + HKDF-SHA256 派生 per-pair key + ChaCha20-Poly1305（v0.4 已实现）
- 信令 TLS（v0.8 已实现）：服务器 `--tls-cert/--tls-key`，客户端 `--tls` 等
- 常数时间比较（`hmac.Equal`）；128 位随机 PeerID / nonce；96 位随机 STUN TID

**数据面加密（v0.4 已实现，采用方案 B）**：

1. `Candidate` 新增 `x25519_pub` 字段（每会话临时公钥），随现有候选交换分发，**无新增握手消息**；打洞开始前双方已互持公钥
2. 双方各自计算：`key = HKDF-SHA256(X25519(myPriv, peerPub), info = "p2p-data-v1:<room>:<排序后的双方PeerID>")`
3. punch 帧**复用现有 41 B 头**，`len` 字段覆盖 nonce+密文：

```text
payload = [12B 随机 nonce][AEAD-ChaCha20-Poly1305(mesh 帧 + 16B tag)]
```

4. mesh 帧整体作为 payload 被加密：mesh 层与上层协议栈**零改动**；链路加密为**逐跳**（每跳用与下一跳的 per-pair key 重新封装），对路径外观察者不可见；v0.22 起单播应用载荷额外做**端到端加密**，中间节点无法读取应用数据
5. 兼容性：双方都携带公钥时自动加密；任一方缺失（旧版）则回退明文，因此新旧节点可互通

*方案 A（文档2 原案）——Noise XK 握手*：身份静态公钥注册在信令服务器，1-RTT 握手、身份绑定最强；但需信令下发公钥、独立握手状态机，改动面大。当前未采用，可作后续演进。

**配套加固**（P1 已完成，后续可选）：
- 中继注册加固已完成：信令签发 per-peer relay token，中继按 peer 校验（v0.9）
- 服务器限流已实现：每 IP 连接数、每房间成员数上限（`--max-conns-per-ip` / `--max-room-members`）；可选后续：房间创建频率限制（S4）
- 信令 TLS 已实现（v0.8，`--tls-cert/--tls-key` + 客户端 `--tls`）；主动防御沿用既有双向 HMAC

### 11.5 质量验收指标（提案，待实测基线）

当前无 benchmark/性能基线，以下目标为提案值，落地时以实测校准：

| 指标 | 目标 | 测量方法 |
|---|---|---|
| 二进制体积 | client ≤ 6 MB / server ≤ 4 MB（维持现状） | 构建产物大小（`-s -w`） |

## 14. 开发约定

1. **依赖方向**：`cmd → sdk → core/* → core/protocol`，core 包间单向、无环；平台差异用 build tags（`//go:build windows`），不写 `runtime.GOOS` 分支到公共逻辑。
2. **回调约束**：`Listener.OnEvent` 与 mesh `OnData` 从网络读循环调用，**必须快速返回且不得回调 Session**（Android 端用 `mainHandler.post` 切主线程）。
3. **wire 协议变更**：先改 `core/protocol` 与帧编解码，同步更新 §6 表格；`omitempty` 字段只增不删。
4. **并发**：`Session`/`Hub`/`Punch`/`mesh.Node` 均以 `mu` 保护状态；网络写侧注意 `member.mu` 式的串行化（信令广播会从多 goroutine 写同一连接）。
5. **错误上报**：SDK 内错误一律 `emit(EventError,...)`，不 panic；CLI 打印后退出码非零。
6. **文档**：行为变化同步更新本文档 §12 与 `README.md`；设计讨论放 `docs/design/`。
